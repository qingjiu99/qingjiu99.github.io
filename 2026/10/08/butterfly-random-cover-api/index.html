为什么随机封面还是会重复：Butterfly 主题的去重机制分析

发表于2026-10-08|更新于2026-10-09|技术
|总字数:2388|阅读时长:10 分钟|浏览量:

给 Hexo 博客配置随机图片 API 后，我发现不同文章的封面并不是永远不重复：有时连续几篇文章会出现相同或相似的图片。进一步查看 Butterfly 主题的实现后，才发现这里的“随机”与“唯一”是两回事。

当前配置了多少个 API

现在使用的是 UapiPro 随机图片接口，通过 category 参数选择不同类别：

列表里一共 7 个候选地址，覆盖 acg（二次元动漫）、anime、landscape（风景）、furry 等类别，最后一项不指定 category，走全局随机。

其中 type=mb 是移动端尺寸。该接口支持 type 子类别，mb 返回的图片明显更小，实测约为 200 KB，而不带 type 的同一类别可能达到 1 MB 以上，对手机访问更友好。

这些地址在配置时都实际返回了图片响应。需要注意的是，接口文档中列出的其他类别（例如 ai_drawing、ikun）在本次测试时返回 404，因此没有加入配置。第三方 API 的可用性会变化，后续如果某个地址失效，需要替换或删除。

一次封面变成 404 插图的排查

配置完成后，首页出现过一张明显的 “404 ERROR” 插图。这里记录一下排查过程，因为它很容易被误判成接口挂了或者博客部署出错。

404 插图其实来自主题

Butterfly 的文章封面是这样渲染的：

也就是说，只要封面图片加载失败，不管是接口返回错误、连接超时还是跳转目标不可达，浏览器都会用主题自带的 /img/404.jpg 顶上去。所以看到这张插图，只代表”这张图没加载出来”，不一定是接口真的返回了 HTTP 404。

定位到具体类别

逐个类别做多次请求统计后，问题范围很快缩小了：

类别 8 次请求成功率
acg 8/8

只有 general_anime&type=mb 会不稳定地失败。

为什么它不稳定

跟踪跳转地址后发现，general_anime 并不是由 uapis 自己托管图片的类别，而是聚合类：每次请求都会 302 跳到一个随机第三方图床。

同一个类别，连续几次请求可能落到完全不同的上游：

只要这次抽到的上游不可用，封面就加载失败，于是显示 404 插图。也就是说，失败不是配置文件写错了，而是上游图床的可用性完全不受我们控制。

相比之下，acg、anime、furry 这些类别最终都指向 uapis 自己的资源：

同源、可控，因此稳定得多。

处理方式

最终选择最直接的方案：把 general_anime&type=mb 从候选列表里删掉，保留其余 7 个稳定类别。

如果确实需要这类聚合图片，也可以保留它，但要接受偶发的兜底插图；更稳妥的做法是把它换成静态图片，或者在文章 front matter 里为重要文章单独指定本地封面。

为什么 API 参数不能保证图片唯一

即使文章引用的是不同类别的 URL：

服务端仍可能返回相同或相似图片，原因包括：

  • 查询参数没有被服务端用作图库分区。
  • API 使用自己的随机数生成器，可能重复抽到同一张图。
  • CDN 或浏览器缓存了重定向结果。
  • API 返回的是临时跳转地址，最终图片地址可能相同。
  • 图片库本身数量有限。

所以“URL 不同”不等于“图片内容不同”。

构建时随机与访问时随机

Butterfly 的默认封面是在 Hexo 构建过程中分配的。构建时，主题会给每篇文章写入一个封面 URL；推送到 GitHub Pages 后，静态 HTML 已经生成。

但是，如果这个 URL 本身是随机 API：

那么同一篇文章每次被浏览时，API 都可能返回不同图片。也就是说：

  • 文章之间的 API 地址可能不同。
  • 同一篇文章刷新页面后，实际图片也可能变化。
  • 重新构建博客时，文章分配到的 API 地址还可能再次变化。

这也是“构建时随机选择”和“请求时随机返回”叠加后的结果。

方案二：改成整批图片不重复

如果希望一次构建中每篇文章都使用不同图片，就需要修改主题的随机逻辑：

  1. 构建开始时建立候选图片索引。
  2. 随机打乱整个索引数组。
  3. 按文章顺序依次取出图片。
  4. 候选图片用完后再重新开始一轮。

这种方式可以保证在图片池用完前不重复，但需要维护主题源码或写 Hexo 插件，升级 Butterfly 时也要重新检查兼容性。

顺手做的两项性能优化

随机图片接口虽然方便，但它是首页最重的资源。实测时，单个接口响应时间大多在 0.5 到 2 秒之间，图片大小从几百 KB 到 1.6 MB 不等。首页如果一次加载十几张远程封面，流量和等待时间都会明显上升。

因此这次同时调整了两个地方。

第一，开启图片懒加载：

Butterfly 会为页面中的图片加上原生懒加载属性：

浏览器因此会优先加载首屏附近的图片，下方文章封面等接近可视区域时再请求。

第二，减少首页文章数量：

首页卡片数量减少后，首屏需要请求的远程封面也相应变少，移动网络下的体感会更明显。

需要说明的是，懒加载解决的是“什么时候请求”，不能减少单张图片的体积。如果封面本身有 1 MB 以上，滚动到该位置时依然要等待。所以要继续提速，仍然需要控制图片大小，例如优先使用 type=mb 这类小尺寸，或改用压缩后的本地图片。

我的选择

目前博客使用同一个随机图片服务的 8 个不同类别候选地址，配合懒加载和首页 6 篇文章。这样既有视觉变化，又不会像之前那样让首页一次拉取大量远程大图。

本文中的接口来源与参考资料：

  • UapiPro 随机图片接口文档
  • 十五个免费随机图片 API 接口网站（CSDN）

如果希望长期稳定、可控并且便于缓存，建议逐步换成本地图片，并为重要文章显式指定 cover。

随机带来变化，固定带来可控；在静态博客里，后者通常更适合正式内容。

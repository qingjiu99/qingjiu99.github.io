用 DeepSeek 从零搭建这个博客：完整教程

发表于2026-10-01|更新于2026-10-09|技术
|总字数:2532|阅读时长:10 分钟|浏览量:

这个博客从一行配置到正式上线，全程有 DeepSeek 参与。这篇把完整流程、真实命令、以及我实际踩过的坑都记下来，给同样想搭站的朋友一份可以直接照做的参考。

为什么用 AI 辅助建站

搭建一个静态博客，技术上并不难，难的是信息太碎。

Hexo 的配置项散在官方文档各处，主题的目录结构各家不同，部署到 GitHub Pages 又要处理仓库命名、分支、代理、凭据一堆细节。对不熟悉前端工具链的人来说，真正的门槛不是”不会写代码”，而是不知道该查什么——报错信息往往是 ENOENT 或超时，看不出下一步该干什么。

DeepSeek 在这里的价值很具体：

  • 把模糊需求翻成可执行命令。”我想搞个博客”→ 该装什么、装哪个版本、配置文件放哪、字段怎么写
  • 翻译报错。把一屏看不懂的输出丢过去，能直接告诉我卡在哪一环
  • 充当检查清单。每一步做完让它核对一遍，比自己对文档快很多

但要说明的是：AI 不是万能的。本次搭建中有两个坑，AI 一开始没预料到，是靠实际执行才暴露出来的（见下面「我踩过的四个坑」）。所以正确的用法是 AI 给方案、你负责验证，而不是无脑复制粘贴。

整体路线

选定的是 Hexo + GitHub Pages 这套组合，理由很实际：

方案 优点 缺点
Hexo + GitHub Pages 纯静态、加载快、免费、仓库即备份 需要本地环境
WordPress 后台可视化 要服务器和数据库
语雀 / 知乎等平台 零成本 数据不在自己手里，样式受限

写文章只需要 Markdown，内容以纯文本存在自己电脑上，发布就是一次 git push。对个人博客来说足够了。

我踩过的四个坑

这部分是本文最有价值的地方——都是实际执行时才暴露出来的。

坑一：npx 找不到

原因：Node.js 根本没装，或者装了但没进系统 PATH。项目里即使有 node_modules，缺了运行时照样跑不起来。

排查：开个新终端敲 node -v。如果报错，就是环境问题，和项目无关。

坑二：GitHub 连不上

原因：国内直连 GitHub 普遍不通。注意：光开着代理软件不一定够——git 底层用的是 libcurl，不一定读取系统代理设置，需要显式给 git 设环境变量：

端口号填你代理软件的实际端口（Clash 常见的是 7890 或 7897）。

能返回内容就说明代理正常。

坑三：登录窗口关不掉

首次部署会弹出 Connect to GitHub 授权窗口。选 「Browser/Device」 标签页，点 「Sign in with your browser」，浏览器里完成授权。

但有个坑：有时候推送其实已经成功了，这个窗口却还挂在屏幕上不消失。

怎么判断：去看命令行的输出。如果已经出现下面这两行，说明部署完成，窗口是残留：

这时直接点右上角 ✕ 关掉就行，不要再点授权按钮，否则会触发一次多余的授权流程。

坑四：网站显示的是别人的内容

这个坑最唬人。推送成功后打开网站，标题变成了完全陌生的名字，自己的文章页全是 404。

原因：Pages 还在重建，浏览器拿到的是上一次部署的旧站。如果这个仓库之前放过别的内容（比如从模板 fork 来的），你会看到那个模板的内容。

解决：等 1～2 分钟再刷新。如果超过 5 分钟还是旧内容，再去仓库 Settings → Pages 检查构建状态。

和 AI 协作的几点心得

搭完之后回头看，用 DeepSeek 辅助建站确实省了时间，但有几个心得值得记下来：

  1. 让它给命令，而不是给结论。问”怎么部署”，不如问”我要把本地 Hexo 推到 GitHub Pages，给我完整命令和每一步的作用”
  2. 报错原样贴给它。不要自己概括成”部署失败了”，完整的报错信息里往往藏着关键线索
  3. 每一步都验证。AI 给的方案可能基于旧版本，或者漏掉你这个环境的特殊情况（比如本次的”Node 没装”）
  4. 让它解释为什么。知道”为什么这么配”比知道”这么配”更重要，出问题时才有排查方向

最后一点体会：AI 能帮你把博客搭起来，但写不出你的文章。 工具解决的是”能不能写”，真正难的是”写什么”。
